# Wire notes

Explanatory notes on wire semantics that JSON Schema cannot carry. Machine-readable JSON Schema, errors, examples and vectors remain authoritative: where a note and a Schema disagree, the Schema wins and the note is a defect.

## Alarm code `SLOT_EXPECTED_ACTION_OVERDUE`

Source: CP-0005 section 4.1 (REQ-0358).

- `AlarmEntry.code` is an open set of strings, not an enum, so registering this code changes no schema.
- The onboard HMI raises it in `OnboardAlarmSnapshot` when the current slot of a slot operation has waited for the operator beyond the configured threshold.
- `subjectType` is `SLOT` and `subjectId` is the slot number.
- `raisedAt` is the instant the wait crossed the threshold.
- `displayMessage` is the action the vehicle expects.
- The time already waited is derived from `raisedAt` and the threshold. `OperationProgress` (`phase` `WAITING_OPERATOR`, `activeUnlockSlots`) may help, but it is `TELEMETRY` and can be lost, so it is never the basis.
- The slot readings (`lockState`, `physicalState`, `unlockOutputState`) are taken from `SafetyStateSnapshot`.
- This alarm is the precondition of `SlotFaultDeclarationCommand`: an administrator can declare a fault only on a current slot that has reported it (REQ-0359).

## `SublotEntryRequested.expiresOnRevisionChange`

Source: specification 23.5.

- The field stays `const: true`; neither its value nor its type changes.
- `true` means the entry request expires on a revision change, and a revision change is: the stop ended, the operation session or the station changed (a worklist for another operation session or station with a strictly higher revision), the worklist became empty (a worklist no older than the entry request with empty `items`), or the control server rejected the submission with `WORKLIST_REVISION_STALE`. A worklist revision advancing within the same operation session at the same station is not a revision change, and the entry request stays open.
- Separately from expiry, a `LOAD` `SlotOperationCommand` of the same operation session answers the entry request and so ends it.

## Staging pickup stops

Source: CP-0012 (program#185) section 3, protocol#13; CP-0014 (program#191) section 3 item 4, protocol#17.

- A staging pickup stop is a pickup stop at the fixed origin station of `STAGING_TO_WIRE`, the staging station. Pickup stops at machine stations keep every rule below unchanged.
- `CurrentStopWorklistSnapshot.stationDepartureDeadlineAt` is always `null` at a staging pickup stop: the stop has no station departure deadline and no countdown.
- At a staging pickup stop, as at a machine pickup stop, `VehicleBusinessStateSnapshot.loadingPhase.state` is `LOADING` while a demand of this stop remains to be loaded, and `CARGO_HOLDING_WAIT` once none remains and at least one basket is loaded. `cargoHoldingDeadlineAt` is `null` until a basket is loaded, as the program#94 table gives `null` before the first load batch closes safely.
- Once a basket is loaded `cargoHoldingDeadlineAt` is set, counted from the safe closure of the load batch that put cargo on board, with the same duration as at a machine pickup stop. Each demand with this station as its pickup station appended to the vehicle afterwards moves it to the time of the append plus that duration; a release, a cancellation or any other worklist change does not move it. This is the one difference from a machine pickup stop, whose `cargoHoldingDeadlineAt` never moves once given. If the cargo is undone until no basket is loaded, the deadline returns to `null`, and the next loaded basket sets it afresh.
- `cargoHoldingDeadlineAt` may be non-null in either state, `LOADING` or `CARGO_HOLDING_WAIT`: the onboard HMI shows the cargo-holding countdown from `cargoHoldingDeadlineAt` alone, never from `state`. A demand appended for this station opens a new stop at it, so `state` returns to `LOADING`, carrying the moved deadline, until that demand is loaded. At a machine pickup stop likewise, once the first load batch closes safely while loads committed to the stop remain, `state` is `LOADING` with `cargoHoldingDeadlineAt` already set (ADR-cross-0057).
- When the cargo-holding deadline expires at a staging pickup stop, the loading phase ends as at a machine pickup stop: `loadingPhase` is `CLOSED` with `closedReason` `CARGO_HOLDING_TIMEOUT`, the loaded demands stay on the journey, and demands not yet loaded are released back to dispatch, never cancelled or suppressed and never counted against the station-timeout release limit; if an empty worklist is sent because of the release, it carries `stopEndedReason` `DEMAND_RELEASED`, as at a machine pickup stop. The expiry does not interrupt a running slot operation, load correction or cancellation; the phase ends once it settles. The vehicle leaves through the correction gate and the `DEPARTURE` safety check as before, with no further correction grace.
- When a staging pickup stop ends because the operator departed or because the vehicle must charge, and demands not yet loaded are released back to dispatch, the empty worklist carries `stopEndedReason` `OPERATOR_DEPARTED` or `CHARGING_REQUIRED`, never `DEMAND_RELEASED` and never a timeout reason: those two belong to the expiry above. When every demand of the stop is loaded the vehicle leaves as before and no empty worklist is sent. A vehicle holding cargo already shows an empty worklist; if the control server sends another one after a departure, it carries `OPERATOR_DEPARTED`.

## `CurrentStopDepartureRequested` and `CurrentStopDepartureResult`

Source: CP-0012 (program#185) section 3, protocol#13; CP-0014 (program#191) section 3 item 4, protocol#17; CP-0015 (program#201) and control-server#742, protocol#23.

- The control server accepts a departure request at a staging pickup stop, and at a machine pickup stop once every load committed to that stop is complete, at least one basket is loaded and the vehicle has not yet asked to leave, whether the vehicle is still in cargo-holding wait or its loading phase has already ended and only the station departure wait remains. The `loadingPhase` the vehicle shows does not decide this: on a journey that does not hold cargo, because every zone the vehicle serves forbids en-route appends, it still reads the last `LOADING` sent. The message itself is not scoped to a task type, and the request is refused elsewhere.
- The onboard HMI journals the request before it sends it. Each press mints one `departureRequestId`; a resubmission of the same press, including after a restart, reuses it.
- The request echoes the worklist the vehicle shows: its `stationId`, `worklistRevision` and `operationSessionId`. The control server identifies the stop by `stationId` and `worklistRevision`. `operationSessionId` is `null` when that worklist carries none, as every empty worklist does, so a vehicle holding cargo at the staging station with an empty worklist can still depart.
- The control server answers every request with `CurrentStopDepartureResult`. It checks in this order and the first check that fails decides: `STATION_MISMATCH` when `stationId` is not the vehicle's current stop; `WORKLIST_REVISION_STALE` when `worklistRevision` is not the current worklist revision of that stop (`currentWorklistRevision` names it) and the exception for a stale revision without material change below does not apply; `ACTION_NOT_ALLOWED_IN_STATE` when the stop accepts no departure in its present state: a machine pickup stop whose committed loads are not all complete or that has no basket loaded, a stop that is not a pickup stop, a vehicle that has already asked to leave, a running slot operation, an open load correction or a cancellation in progress. A `REJECTED` result carries that `Problem` and changes no business state. `ACCEPTED` carries no `Problem`.
- At a machine pickup stop, when the `worklistRevision` of a departure request is not the current one, the two revisions differ in nothing material only when all of the following hold: (1) the requested revision is lower than the current one, lies within the worklist revisions of the current stop itself, and the worklist of that revision has the current station as its `stationId`; (2) when the request carries an `operationSessionId`, it equals the current stop's; a `null` one is not compared; (3) every worklist sent for this stop, from the requested revision up to and including the current one, has empty `items`; (4) since the requested revision no load has settled at this stop, none of the baskets already loaded has left it (terminated or removed), and no load correction has been opened at it; when a load settled and when a correction was opened are taken at the control server's receipt. If any of them fails the answer is still `WORKLIST_REVISION_STALE`. If all hold, the request is decided by the remaining checks, and answered `ACCEPTED` when they pass. The exception does not apply at a staging pickup stop. A control server that does not record when a basket left the stop may treat every basket loaded at this stop that is no longer loaded as having left it since the requested revision, and so fail (4); that is only more conservative: the worst outcome is a `WORKLIST_REVISION_STALE` where an `ACCEPTED` was possible, and the operator presses again.
- After `ACCEPTED` the departure travels in the existing snapshots. At a staging pickup stop it goes as follows. With at least one basket loaded, `loadingPhase` is `CLOSED` with `closedReason` `OPERATOR_DEPARTED`, the loaded demands stay on the journey, and the vehicle leaves through the correction gate and the `DEPARTURE` safety check as before. With nothing loaded the journey closes, `loadingPhase` is `null`, and the vehicle stays where it is. Either way demands not yet loaded are released back to dispatch, never cancelled or suppressed and never counted against the station-timeout release limit.
- At a machine pickup stop accepted in `CARGO_HOLDING_WAIT`, the departure counts as the cargo-holding deadline expiring now: `loadingPhase` is `CLOSED` with `closedReason` `OPERATOR_DEPARTED`, not `CARGO_HOLDING_TIMEOUT`, so the vehicle tells a press from an expiry; the loaded demands stay on the journey, and appended stops not yet loaded are released back to dispatch as on a cargo-holding timeout, never cancelled or suppressed and never counted against the station-timeout release limit. Accepted after `loadingPhase` has ended, `loadingPhase` stays as it was, `closedReason` included. Either way the stop ends at once: the vehicle does not wait out the rest of the station departure deadline (`stationDepartureDeadlineAt`), keeps no correction grace, and leaves through the correction gate and the `DEPARTURE` safety check; an empty worklist sent for it carries `stopEndedReason` `OPERATOR_DEPARTED`.
- The same `departureRequestId` with the same content is answered by replaying the stored result exactly as it was first decided, `currentWorklistRevision` included, never recomputed, and has no second effect.
- The same `departureRequestId` with different content is answered with `ProtocolProblem` carrying `BUSINESS_ID_CONTENT_CONFLICT`. No `CurrentStopDepartureResult` is sent for it and it is not applied.

## Charging required at a staging pickup stop

Source: CP-0013 (program#188) section 3, protocol#15. It replaces the charging stop CP-0012 section 3 gave this candidate: the vehicle delivers its cargo first and charges afterwards. No schema changes; the Schemas already allow these values.

- At a staging pickup stop with at least one basket loaded and no slot operation running, a vehicle below the mandatory charge line departs as for an accepted departure, decided by the control server and not by an operator. `loadingPhase` is `CLOSED` with `closedReason` `CHARGING_REQUIRED`, the loaded demands stay on the journey, and demands not yet loaded are released back to dispatch, never cancelled or suppressed and never counted against the station-timeout release limit. The vehicle leaves through the correction gate and the `DEPARTURE` safety check as before.
- The journey goes on to its existing dropoff stops and carries no charging stop: `UpcomingStopPlanSnapshot` gains no `CHARGER` leg, `activePurpose` stays `TRANSPORT` and `chargingCycleState` stays `NOT_CHARGING` while the journey lasts. `batteryState` may read `MANDATORY_CHARGE` meanwhile; the journey is not interrupted to charge. Every departure on it is a `PreDepartureSafetyCheck` with `checkPurpose` `DEPARTURE`, as on any transport journey.
- Once the journey ends the existing charging allocation takes the vehicle, as it takes any vehicle without a purpose below the mandatory charge line: `activePurpose` becomes `CHARGING`, its moves are `NON_BUSINESS_MOVE` checks, and `chargingCycleState` runs from there. The vehicle does not return to the staging station before it charges.
- Without cargo the journey closes instead, `loadingPhase` is `null`, and the existing charging allocation takes the vehicle, so `closedReason` `CHARGING_REQUIRED` appears only with cargo on board.

## `TransportTaskType` `WIRE_TO_FULL_INSPECTION`

Source: the user's decisions 6 and 7 of 2026-10-16 in program#195, protocol#21.

- `WIRE_TO_FULL_INSPECTION` is the seventh transport task type: lots go from wire bonding machines to the full-inspection area. Its destination is the area, a public station, not a machine in it. The full-inspection area is a different place from the `WIRE_TO_GATE` quality gate.
- It is appended to `TransportTaskType`, the closed enum of `CurrentStopWorklistSnapshot.items[].workType`, the one message field that carries a task type. The six released values keep their order and meaning.
- Appending a value to a closed enum is breaking (`docs/release-governance.md`): a 4.0.0 implementation rejects a message carrying `WIRE_TO_FULL_INSPECTION` as `PROTOCOL_SCHEMA_INVALID`, so both implementations move to 5.0.0 together, in one package, and no 4.0.0 peer is ever connected to a 5.0.0 one. The exact `ProtocolReleaseIdentity` check already refuses such a pair at the handshake.
- `PublicStationFunction` is unchanged: it gains no `FULL_INSPECTION`. Specification 5.3 no longer maintains that field: the control server sends `publicStationFunction` as `null` on every leg except a staging pickup leg, where it sends `WIRE_STAGING` (control-server#713), and nothing sends `FULL_INSPECTION`. The user decided on 2026-10-16 not to add it.
- The value is spelled exactly `WIRE_TO_FULL_INSPECTION`, as the MES `TASK_TYPE` literal; a misspelled or lowercase spelling is schema-invalid, like any value outside the enum.

## `UpcomingStopPlanSnapshot` carries the remaining plan

Source: the user's decision of 2026-10-17, CP-0015 (program#201) revision of REQ-0196, protocol#23. No schema changes.

- The plan holds the vehicle's current stop and the stops after it that are not yet complete. Stops already passed are not sent, and the onboard HMI shows none. This holds for every plan except one, the clearance move below.
- The one exception is a clearance move off a charger, the plan sent while `activePurpose` is `CLEARING_MAINTENANCE`: while the vehicle drives from the suspended charger to a waiting point, the plan keeps the `CHARGER` leg it left, as `COMPLETED`, ahead of the waiting point leg. The onboard HMI names the charger of the clearance from that leg (control-server#406), and the clearance goes on after the vehicle has left the charger. No other plan sends a stop already passed.
- At most nine legs remain, as `legs` `maxItems` 9 has always allowed.

## `RemainingBasketsSkipRequested` and `RemainingBasketsSkipResult`

Source: CP-0021 (program#213) new item 1 (REQ-0367) and the revised REQ-0211 and REQ-0352, requirements-baseline-v1.20.0; protocol#26.

- At a pickup stop, machine or staging alike, a `LOAD` slot operation of a demand whose expected basket count N is greater than 1 may end short. Once k of its target slots, 1 <= k < N, have closed safely `OCCUPIED` (a basket in, the door proven locked, the unlock output proven reset), the operator may ask to leave the remaining baskets, and the demand then completes with the k baskets as a normal delivery. This is not a cancellation: the demand is not terminated with `CANCELLED_BY_OPERATOR`, nothing is suppressed, no loaded slot is cleared, and no manual transport alarm is raised. With nothing loaded, giving the demand up is a cancellation under REQ-0211.
- The onboard HMI never ends a load short on its own: only a `RemainingBasketsSkipResult` with `outcome` `AUTHORIZED` lets it. It offers the skip only while at least one target slot has closed safely `OCCUPIED`, at least one has not, every target door is proven locked, every unlock output is proven reset, no slot is `UNKNOWN` and the operation has not gone to manual recovery. Each press mints one `skipRequestId`; the onboard HMI journals the request before it sends it, and a resubmission of the same press, including after a reconnect or a restart, reuses it. It opens no further slot while the request is pending, and it has at most one request of a demand pending. After `REJECTED` it goes on loading, shows why, and a later press is a new request with a new `skipRequestId`.
- `loadedSlots` are the k target slots of `slotOperationAttemptId` that have closed safely `OCCUPIED`, at least one, so a request for k = 0 cannot be written. `operator` is the operator when the vehicle knows one and `null` otherwise; it is recorded and is never a reason to refuse.
- The control server answers every request with `RemainingBasketsSkipResult`. It checks in this order and the first check that fails decides: `DEMAND_NOT_CURRENT` when the demand is not a demand of the vehicle's current pickup stop or `slotOperationAttemptId` is not its current `LOAD` attempt; `OPERATION_SESSION_MISMATCH` when `operationSessionId` is not the current stop's; `ACTION_NOT_ALLOWED_IN_STATE` when the load accepts no skip in its present state: the demand's expected basket count is 1, the attempt already has an `OperationResult` (the load has ended), the operation has gone to manual recovery (an exception recovery session or a slot fault declaration), a load correction or cancellation of the demand is in progress, or another skip of the attempt has been authorized; `SLOT_STATE_UNKNOWN` when a target slot is `UNKNOWN`; `LOCK_NOT_CLOSED` when a target door is not proven locked; `UNLOCK_OUTPUT_NOT_RESET` when a target unlock output is not proven reset; `REMAINING_BASKETS_SKIP_NOTHING_LOADED` when by its facts no target slot has closed safely `OCCUPIED`; `SLOT_SET_INVALID` when `loadedSlots` are not exactly the target slots that by its facts have closed safely `OCCUPIED`, or name every target slot so that none remains. Its slot facts are the readings it holds from the vehicle (`SafetyStateChanged`, `SafetyStateSnapshot`); it may ask for a `SafetyStateSnapshot` before it decides. A `REJECTED` result carries that `Problem` and empty `loadedSlots`, and changes no business state.
- `AUTHORIZED` carries no `Problem` and names in `loadedSlots` exactly the k slots of the request. The onboard HMI journals it, opens no further slot, ends the operation and reports `OperationResult` with `overallOutcome` `COMPLETED_REMAINING_SKIPPED` and `remainingBasketsSkipRequestId` set to the request's `skipRequestId`: every authorized slot `COMPLETED`, `OCCUPIED`, `LOCKED` and `RESET`; every other target slot of the command `NOT_STARTED`, `EMPTY`, `LOCKED` and `RESET` with `REMAINING_BASKET_SKIPPED` in its `reasonCodes`, a slot opened earlier and closed empty included. Every other `OperationResult` carries `remainingBasketsSkipRequestId` `null`. If the slots no longer read so when the operation ends, the vehicle reports the result as it would without the skip, `FAILED` or `UNKNOWN`, with `remainingBasketsSkipRequestId` `null`.
- The control server settles a `COMPLETED_REMAINING_SKIPPED` result only when `remainingBasketsSkipRequestId` names a `RemainingBasketsSkipResult` it sent with `outcome` `AUTHORIZED` for the same `demandId` and `slotOperationAttemptId`, its `COMPLETED` slots are exactly that result's `loadedSlots`, and its `NOT_STARTED` slots are exactly the rest of the command's target slots. It then commits the k baskets as one LoadBatch and releases the remaining slots and their reservation at once (REQ-0352). The demand goes on as a load of k baskets: its later `UNLOAD` `SlotOperationCommand` names only the k slots, with `expectedBasketCount` k, while its `CurrentStopWorklistSnapshot` item keeps the demand's `expectedBasketCount` N, which does not change; once unloaded the demand completes as a normal delivery. Any other skipped result -- no authorization, a `REJECTED` one, another demand's or attempt's, or other slots -- is acknowledged with `DurableAck`, and the control server never settles it as completed: it stays unreconciled and the journey is blocked for recovery, as for any result that does not reconcile.
- A pending request never stops the control server from settling an `OperationResult` of the attempt that arrives first; the request is then refused with `ACTION_NOT_ALLOWED_IN_STATE`. A cancellation asked for while a skip is pending or authorized is refused, as every cancellation is once a basket is loaded (below).
- The same `skipRequestId` with the same content is answered by replaying the stored result exactly as it was first decided, never recomputed, and has no second effect. The same `skipRequestId` with different content is answered with `ProtocolProblem` carrying `BUSINESS_ID_CONTENT_CONFLICT`; no `RemainingBasketsSkipResult` is sent for it and it is not applied.
- The control server records each skip with N and k, when it was asked for and decided, and the operator when known, on its dashboard and in its audit (REQ-0367).
- Under the revised REQ-0211 a load with a basket in any target slot is never cancelled: `LoadCancellationAuthorization` is `REJECTED` with `LOAD_CANCELLATION_BASKET_LOADED`. With nothing loaded but a door not proven locked or an output not proven reset it is `REJECTED` with `LOCK_NOT_CLOSED` or `UNLOCK_OUTPUT_NOT_RESET`. Once loading has started a cancellation is authorized only with every target slot `EMPTY`, every door proven locked and every output reset, and then with empty `slots`: no door is opened to clear it. The clearing a cancellation used to command keeps its messages and vectors in this candidate; a control server following REQ-0211 no longer authorizes one.
