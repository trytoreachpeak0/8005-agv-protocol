# Candidate limitations and release finalization

The candidate intentionally uses structurally valid synthetic zero hashes inside envelope examples. Examples are schema fixtures, not evidence of a materialized release identity.

The manifest/approval circularity is resolved by the owner-approved governance separation recorded on 2026-08-25. `manifest/release.json` is an approval-neutral content snapshot and excludes `attestations/`; a completed external `release-approval.json` GitHub Release Asset binds the final immutable candidate commit and content manifest hash. The repository tracks only its blank Schema-governed template. G1 validates both artifacts and reports both hashes for the annotated tag and GitHub release metadata.

`protocol-v0.1.0`, `protocol-v0.1.1` and `protocol-v0.2.0` remain immutable; each was created with an approved external attestation. The current `0.3.0` superseding candidate is **breaking** and raises ProtocolVersion from 2 to 3. Its attestation remains `PENDING`; the product owner must approve the new exact commit, content manifest hash, vectors hash and the breaking classification before `protocol-v0.3.0` can be created. Release approval has carried exactly one product owner since 2026-09-08; AI and CI still cannot approve.

The `0.3.0` candidate closes the contract gap recorded as `8005-agv-control-server` issue #5: `ExceptionRecoverySessionOpened`, `RecoveryActionAccepted` and `ExceptionRecoverySessionSnapshot` each gain a required, nullable `slotOperationAttemptId`. `LoadCompensationRequested` requires that identity, and no server-to-vehicle message carried it, so a vehicle whose own attempt record had already been cleared could never assemble the request. The field is nullable because a recovery session opened before any slot operation started has no attempt to name — the same reason `demandId` is nullable in the same payloads.

The candidate also puts the station departure deadline on the wire: `CurrentStopWorklistSnapshot.payload` gains a required, nullable `stationDepartureDeadlineAt`. ADR-cross-0055 is accepted, it places the StationDepartureWaitTimeout in the server's hands, and it states that the vehicle displays only the server's deadline — its Consequences require the onboard screen to show the remaining time throughout, yellow for the last 60 seconds and flashing red per second for the last 10. No message could carry that instant: every `Instant` on the 28 C_TO_O payloads records when something happened, not when something is due. `CurrentStopWorklistSnapshot` is the carrier because the reset is not a separate event — in the server, closing a load round sets the new wait start and republishes the worklist in the same step, so the deadline and the revision it belongs to travel together. The field is nullable because a stop with no continuing load has no deadline: ADR-cross-0055 ends a pure unloading stop as soon as unloading completes.

The candidate also appends `OPERATOR_TIMEOUT` to the error registry. ADR-cross-0058 settles an operator inaction deadline as a determinate failure when the slot door is already closed, and no existing code expresses that: `LOCK_NOT_CLOSED` covers only the door-still-open path. The ADR left the decision to the next protocol batch; this is that batch.

The `0.2.0` candidate, now released as `protocol-v0.2.0`, removed the single-demand narrowing the MVP had frozen into the contract: `CurrentStopWorklistSnapshot.items` accepts up to the vehicle's eight slots instead of exactly one, `UpcomingStopPlanSnapshot.legs` accepts a stop sequence instead of exactly two legs and gains `TO_CHARGER`, `SublotEntryRequested` carries `expectedSublots` (the sublots still enterable within this dispatch range, per FR-001 AC-3 and BR-001) instead of a single `expectedSublot`, and `LoadCancellationResult.slotResults` allows the empty result that ADR-cross-0046 requires when no slot operation was ever commanded.
